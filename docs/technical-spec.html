01 — Purpose

Overview

Bouldy is a backend API for climbers to track bouldering gym sessions. A user logs a session at a gym, then records one or more attempts against that gym's routes — each attempt carrying a result on the standard flash / zone / send / project scale. Gyms maintain a shared route catalogue: grade, colour, wall, setter, and a tagged set of climbing styles (hold type, movement, wall angle, technique).

The service is a single FastAPI application backed by PostgreSQL, with schema evolution managed through Alembic and JWT bearer tokens gating user-scoped data.

02 — System Design

Architecture

The application follows a conventional layered structure. Each layer only talks to the one below it:

Request path

  • Routers (app/routers/*) — HTTP surface: path/method definitions, status codes, HTTPException mapping.
  • Schemas (app/schemas/*) — Pydantic models validating request bodies and shaping responses.
  • CRUD (app/crud/*) — query logic, ownership checks, and cross-entity business rules.
  • Models (app/models/*) — SQLAlchemy 2.0 declarative ORM classes mapped to Postgres tables.

Cross-cutting

  • Dependency injection — get_db() yields a scoped Session per request; get_current_user() decodes the bearer token into a User row.
  • Auth boundary — enforced per-route via Depends(get_current_user), not global middleware.
  • Ownership scoping — session and attempt queries always filter by user_id at the CRUD layer, never in the router.

06 — Security

Authentication

Standard OAuth2 password flow with a stateless JWT bearer token — no refresh tokens or session store.

Register

POST /auth/register

Rejects duplicate email or username with 409. Password hashed with Argon2 before storage.

Login

POST /auth/login

OAuth2PasswordRequestForm (username = email). Returns { access_token, token_type: "bearer" }.

Token

HS256, payload {sub, exp}

Expiry: ACCESS_TOKEN_EXPIRE_MINUTES (default 60). Verified per-request by get_current_user.

08 — Invariants

Business Rules

  • 01Flash requires one attempt. AttemptCreate raises a validation error if result = flash and num_attempts != 1 — enforced in the Pydantic layer, before the row is ever built.
  • 02Attempt route must match session gym. create_attempt rejects the attempt if the route's gym_id differs from the session's gym_id — you can't log a send at a gym you didn't check into.
  • 03Sessions and attempts are owner-scoped. Every query filters on Session.user_id == current_user.id; a mismatch returns 404, not 403, so a session's existence isn't leaked to other users.
  • 04Gyms with routes can't be deleted. delete_gym raises GymHasRoutesError, mapped to 409 Conflict, if any route still references the gym.
  • 05Retiring is its own action. status isn't part of RouteUpdate; only PATCH /routes/{id}/retire can move a route to retired, and it always stamps retired_date to today.

10 — Verification

Testing

~720 lines across five suites (test_auth, test_gyms, test_routes, test_sessions, test_attempts), run with pytest against FastAPI's TestClient.

Isolation: get_db is overridden to a StaticPool in-memory SQLite engine per test run — never Neon — with PRAGMA foreign_keys=ON enabled explicitly, since SQLite ignores FK constraints by default.

Auth bypass: get_current_user can be overridden to a fixed User fixture, so protected endpoints are tested without minting real JWTs.

11 — Open Items

Known Limitations

Gym and route catalogue endpoints carry no auth dependency. Anyone can create, edit, or delete gyms and routes without a token, while sessions and attempts are strictly owner-scoped — an inconsistency worth resolving before this is exposed beyond a trusted client.

  • SQL echo is on in the shared engine (echo=True in app/database.py) — fine for development, noisy and unwanted in production logs.
  • No user-update endpoint is wired up — UserUpdate exists in schemas and app/routers/users.py is registered but empty.
  • Two "initial schema" migrations (8e51f40f1c2e, 3e859f5db2ec) suggest an early rebase; harmless once applied, but worth a comment for future readers of the migration log.
  • Root-level app/schemas.py is an empty file alongside the app/schemas/ package — dead weight that can be removed.
